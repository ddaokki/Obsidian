# 분산 시스템 제3장: 프로세스 (Processes) 기초 상세 학습 노트
**Subject:** 분산 시스템 및 컴퓨팅 **Scope:** Chapter 3 (Main Slides 2-7) **Goal:** 프로세스와 스레드의 차이, 분산 시스템에서의 스레드 활용성 및 자원 관리 비용 이해
## 1. 장 개요 (Chapter Overview)
### 1.1 프로세스의 정의
- **기본 정의:** 실행 중인 프로그램 (A program in execution).
### 1.2 운영체제(OS) vs 분산 시스템(DS) 관점
- **OS 관점:** 프로세스의 관리와 스케줄링(Management and scheduling)이 가장 핵심적인 이슈입니다.
- **분산 시스템 관점:** 시스템의 효율적인 조직과 통신 성능이 더 중요하게 다뤄집니다.
- **멀티스레딩(Multithreading):** 클라이언트-서버 시스템을 효율적으로 구성하는 데 매우 유용합니다.
- **이점:** 스레드를 사용하면 통신(Communication)과 로컬 처리(Local processing)를 동시에 진행(Overlap)할 수 있어 대기 시간을 획기적으로 줄일 수 있습니다.
### 1.3 가상화 (Virtualization)
- 최근 몇 년 사이 분산 시스템에서 매우 중요해진 개념입니다.
- **정의:** 애플리케이션과 해당 실행 환경(운영체제 포함)을 하드웨어와 분리하여 다른 애플리케이션과 동시에 실행할 수 있게 합니다.
- **이점:** 하부 하드웨어나 플랫폼에 대한 의존성을 낮춰 **이식성(Portability)**을 극대화합니다.
## 2. 스레드(Threads)의 필요성
### 2.1 입립성(Granularity)의 한계
- **프로세스 단위:** 일반적인 OS가 제공하는 프로세스 단위의 관리만으로는 분산 시스템의 복잡한 요구사항과 성능을 만족시키기에 부족함이 있습니다.
- **스레드 단위:** 스레드 단위로 작업을 쪼개면 분산 애플리케이션을 구현하기가 훨씬 수월해지며, 결과적으로 시스템 전체의 성능 향상을 가져옵니다.
## 3. 스레드 도입 (Introduction to Threads)
### 3.1 운영체제의 프로그램 실행 방식
- **가상 프로세서:** 운영체제는 각 프로그램을 실행하기 위해 여러 개의 가상 프로세서를 생성합니다.
- **프로세스 테이블 (Process Table):** 운영체제가 이 가상 프로세서들을 관리하기 위해 사용하는 테이블입니다. 여기에는 CPU 레지스터 값, 메모리 맵, 열린 파일 정보, 계정 정보, 권한(Privileges) 등의 정보(Entry)가 포함됩니다.
- **프로세스(Process):** 가상 프로세서 중 하나에서 현재 실행 중인 프로그램 그 자체를 의미합니다.
- **격리와 투명성:** OS는 독립된 프로세스들이 실수나 고의로 서로의 동작을 방해하지 못하도록 철저히 격리하며, 하드웨어를 공유한다는 사실을 사용자에게 투명하게 숨깁니다.
### 3.2 프로세스 동시성 투명성의 비용
여러 프로세스를 동시에 실행하며 '완벽한 격리'를 유지하는 데는 비싼 비용(Overhead)이 듭니다.
- **독립된 주소 공간:** 프로세스를 생성할 때마다 완전히 독립된 주소 공간을 할당해야 합니다.
- **컨텍스트 스위칭(Context Switching) 비용:** CPU가 다른 프로세스로 넘어갈 때 발생하는 오버헤드입니다.
    - 현재 CPU 컨텍스트(레지스터, 프로그램 카운터, 스택 포인터 등)를 저장하고 새 정보를 로드해야 함.
    - 메모리 관리 장치(MMU) 레지스터를 수정하고 주소 변환 캐시(TLB)를 무효화해야 함.
    - 가상 메모리 사용 시 메인 메모리와 디스크 간의 스와핑(Swapping)이 발생하여 속도가 크게 저하될 수 있음.
## 4. 스레드(Thread)의 핵심 특징
### 4.1 스레드의 정의 및 관리
- 프로세스 내에서 독립적으로 실행되는 코드의 흐름입니다.
- **최소 정보 유지:** 성능 최적화를 위해 프로세스 수준의 강력한 격리보다는 CPU 공유에 필요한 최소한의 정보만 유지합니다.
- **스레드 컨텍스트:** 보통 CPU 컨텍스트(레지스터 값 등)와 스레드 관리를 위한 필수 정보만으로 구성되어 가볍습니다.
### 4.2 보호 및 책임
- **개발자의 책임:** 스레드들은 같은 프로세스 내의 주소 공간을 공유하므로, 운영체제가 이들을 서로 보호해주지 않습니다. 따라서 데이터 접근 보호 및 동기화 책임은 전적으로 **애플리케이션 개발자**에게 있습니다.
### 4.3 스레드 사용의 시사점 (Implications)
- **성능적 이점:** 멀티스레드 앱의 성능은 싱글스레드보다 월등히 좋을 수 있으며, 최소한 더 나빠지는 경우는 거의 없습니다.
- **지적 노력:** 스레드는 프로세스처럼 자동으로 보호되지 않으므로, 충돌이나 레이스 컨디션을 방지하기 위해 개발 단계에서 훨씬 더 정교한 **지적 노력(Intellectual effort)**이 필요합니다.

### 5. 비분산 시스템에서의 스레드 활용 (8p)
##### 5.1 싱글스레드 프로세스의 문제
- **블로킹(Blocking) 시스템 호출:** 싱글스레드 프로세스에서 블로킹 호출(예: 입력 대기)이 실행되면 프로세스 전체가 멈춥니다.
- **스프레드시트 예시:** 사용자가 셀 값을 수정하면 모든 의존 셀이 자동 업데이트되어야 합니다. 싱글스레드라면 계산 대기 중에는 사용자의 추가 입력을 처리할 수 없습니다.
##### 5.2 멀티스레드 프로세스의 해결책
- **제어 흐름 분리:** 사용자 인터랙션 담당 스레드와 데이터 업데이트(계산) 담당 스레드를 나눕니다.
- **효과:** 계산이 진행되는 동안에도 사용자는 지연 없이 입력을 계속할 수 있습니다.
### 6. 분산 시스템에서의 스레드 활용 (9p)
##### 6.1 핵심 속성
- **부분 블로킹 방지:** 특정 스레드가 블로킹 시스템 호출을 수행하더라도 프로세스 전체가 멈추지 않고 다른 스레드들이 계속 실행됩니다.
- **복합 연결 관리:** 동시에 여러 개의 논리적 연결(Multiple logical connections)을 유지하고 표현하는 것이 훨씬 쉬워집니다.
- **클라이언트-서버 통신:** 서버의 성능 최적화뿐만 아니라 클라이언트의 대기 시간 은닉에도 필수적입니다.
### 7. 멀티스레드 클라이언트: 지연 시간 숨기기 (10-11p)
##### 7.1 네트워크 지연(Latency)의 현실
- 광역 네트워크(WAN)의 왕복 지연 시간(RTT)은 수백 밀리초에서 수 초에 이를 수 있습니다.
##### 7.2 웹 브라우저 사례
- 브라우저는 웹 페이지 구성을 위해 텍스트, 이미지 등 여러 요소를 각각 TCP 연결을 통해 가져와야 합니다.
- 멀티스레드 브라우저는 텍스트를 먼저 읽어 표시하면서, 동시에 다른 스레드들로 이미지 파일들을 병렬로 페치(Fetch)합니다.
- 사용자는 전체 페이지가 다 올 때까지 기다리지 않고 먼저 도착한 부분부터 상호작용할 수 있습니다.
##### 7.3 서버 복제본과의 병렬 통신
- 웹 서버가 여러 대에 복제(Replication)된 경우, 클라이언트는 여러 복제본에 동시에 접속하여 데이터를 병렬 스트림으로 전송받아 성능을 높일 수 있습니다.
### 8. 멀티스레드 서버: 고성능 모델 (12-14p)
##### 8.1 디스패처/워커(Dispatcher/Worker) 모델
- **디스패처(Dispatcher):** 네트워크로부터 들어오는 요청을 읽고 관리합니다.
- **워커(Worker):** 디스패처로부터 요청을 할당받아 실제 로컬 파일 시스템 작업 등을 수행합니다.
- **이점:** 특정 워커 스레드가 디스크 I/O로 인해 블로킹되어도, 디스패처는 다른 워커를 가동하거나 다음 요청을 계속 받아들일 수 있습니다. (Parallelism 확보)
##### 8.2 스레드가 없는 파일 서버의 한계
- 서버의 메인 루프가 요청을 받고 완료될 때까지 기다리는 구조입니다.
- 디스크 작업 대기 시간 동안 서버는 유휴(Idle) 상태가 되어 다른 어떤 요청도 처리할 수 없습니다.
### 9. 싱글스레드 서버의 성능 개선: 유한 상태 머신 (15p)
##### 9.1 유한 상태 머신(Finite-State Machine, FSM) 모델
스레드 없이 병렬성을 확보하기 위해 싱글스레드를 거대한 상태 머신으로 운영하는 방식입니다.
- **작동 원리:** 요청이 들어왔을 때 캐시에 데이터가 없으면 디스크에 메시지를 보냅니다.
- **비블로킹(Nonblocking) 호출:** 서버는 결과를 기다리며 멈추는 대신, **현재 요청의 상태를 테이블에 기록**하고 즉시 다음 메시지(새 작업 요청 혹은 이전 디스크 작업의 회신)를 처리하러 갑니다.
- **상태 복원:** 메시지를 받을 때마다 테이블에서 해당 계산의 상태를 명시적으로 찾아서 복원(Restore)한 후 작업을 이어갑니다.
- **특징:** 프로세스가 이벤트를 받고 그 내용에 따라 반응하는 유한 상태 머신으로 동작합니다.
### 10. 서버 구축의 3가지 모델 비교 요약 (16p)

|모델 (Model)|특성 (Characteristics)|
|---|---|
|**스레드 (Threads)**|병렬성 제공, 블로킹 시스템 호출 사용 (코딩이 쉬움)|
|**싱글스레드 (Single-threaded)**|병렬성 없음, 블로킹 시스템 호출 사용|
|**유한 상태 머신 (FSM)**|병렬성 제공, 비블로킹 시스템 호출 사용 (매우 복잡함)|

### 11. 가상화의 개념 및 자원 가상화 (17-18p)
###### 11.1 가상화의 정의
- **리소스 가상화 (Resource Virtualization):** 단일 CPU에서 여러 프로그램이 동시에 실행되는 것과 같은 환상(Illusion)을 확장하는 기술입니다.
- 가상화는 기존 인터페이스를 확장하거나 대체하여 **다른 시스템의 동작을 모방(Mimic)** 하는 것을 다룹니다.
###### 11.2 가상화의 역할
- 모든 컴퓨터 시스템은 상위 소프트웨어에 프로그래밍 인터페이스를 제공합니다.
- 가상화를 통해 시스템 B 위에서 인터페이스 A를 구현함으로써, 시스템 A용 프로그램이 시스템 B에서도 동작하도록 만들 수 있습니다.
### 12. 가상화의 도입 배경과 필요성 (19p)
###### 12.1 역사적 배경
- **1970년대:** 고가의 메인프레임 하드웨어에서 기존의 레거시 소프트웨어를 실행하기 위해 도입되었습니다.
- **1990년대:** 하드웨어와 저수준 소프트웨어는 빠르게 변하지만, 미들웨어나 애플리케이션 등 고수준 소프트웨어는 훨씬 안정적입니다. 가상화는 이러한 레거시 인터페이스를 새로운 플랫폼으로 이식(Porting)하는 데 도움을 줍니다.
###### 12.2 관리 및 접근성 측면
- 오늘날의 시스템 관리자는 서로 다른 애플리케이션을 실행하는 대규모의 이기종 서버군을 관리해야 합니다.
- 가상화는 각 애플리케이션을 OS와 라이브러리를 포함한 자체 가상 머신에서 실행하게 함으로써 플랫폼의 다양성을 줄이고 자원 접근성을 높여줍니다.
### 13. 가상 머신 아키텍처와 인터페이스 (20p)
###### 13.1 컴퓨터 시스템이 제공하는 4가지 인터페이스
1. **일반 명령어:** 모든 프로그램이 호출할 수 있는 하드웨어와 소프트웨어 사이의 인터페이스입니다.
2. **특권 명령어:** 운영체제와 같은 특권 프로그램만 호출할 수 있는 인터페이스입니다.
3. **시스템 콜 (System Calls):** 운영체제가 제공하는 인터페이스입니다.
4. **라이브러리 콜 (Library Calls/API):** 대개 시스템 콜을 숨기고 사용자에게 제공되는 API 형태의 인터페이스입니다.
- **가상화의 본질:** 이러한 인터페이스들의 동작을 모방하는 것입니다.
### 14. 가상화의 두 가지 방식 (21-22p)
###### 14.1 프로세스 가상 머신 (Process Virtual Machine)
- 애플리케이션 실행을 위해 추상적인 명령어 세트를 제공하는 **런타임 시스템(Runtime System)** 입니다.
- **특징:**
    - 명령어는 Java 런타임 환경처럼 **해석(Interpreted)** 될 수 있습니다.
    - UNIX에서 Windows 앱을 실행하는 것처럼 **에뮬레이션(Emulated)** 될 수도 있으나, 시스템 콜 모방이 까다롭습니다.
    - 단일 OS 위에서 여러 (애플리케이션, 런타임) 조합의 인스턴스가 실행됩니다.
###### 14.2 가상 머신 모니터 (Virtual Machine Monitor, VMM / Hypervisor)
- 기존 하드웨어를 완전히 차단하고, 그 위에 동일하거나 다른 하드웨어의 전체 명령어 세트를 인터페이스로 제공하는 계층입니다.
- **특징:**
    - 동일 플랫폼에서 여러 개의 서로 다른 운영체제를 독립적이고 동시에 실행할 수 있습니다 (예: VMware).
    - 하드웨어 위에 VMM이 존재하고 그 위에 여러 OS 인스턴스가 올라가는 구조입니다.
### 15. 분산 시스템에서 VMM의 중요성 (23p)
- **보안 및 신뢰성:** 애플리케이션과 그 환경 전체를 격리(Isolation)하므로, 특정 부분의 오류나 보안 공격이 전체 시스템으로 확산되는 것을 방지합니다.
- **이식성 (Portability):** 하드웨어와 소프트웨어를 분리(Decoupling)하여, 전체 환경을 한 머신에서 다른 머신으로 쉽게 이동시킬 수 있습니다.

### 16. 클라이언트와 서버의 상호작용 방식 (24-25p)
###### 16.1 사용자 인터페이스 제공을 위한 두 가지 방식
- **애플리케이션별 전용 구현:** 각 원격 서비스마다 클라이언트 머신에 해당 서비스와 통신할 전용 소프트웨어가 존재하는 방식입니다.
    - **예시:** PDA의 일정 관리 앱이 원격 서버와 동기화되는 경우로, 애플리케이션 계층 프로토콜이 직접 동기화를 처리합니다.
- **사용자 인터페이스만 제공 (Thin-client):** 클라이언트를 단순 터미널로 사용하고 직접적인 서비스 액세스만 제공하는 방식입니다.
    - 모든 처리는 서버에서 수행되며 클라이언트에는 로컬 저장소가 필요 없는 애플리케이션 중립적 솔루션입니다.
###### 16.2 프로토콜의 차이 (그림 3-8)
- **애플리케이션 특화 프로토콜:** 클라이언트와 서버가 특정 앱을 위한 전용 통신 규약을 사용합니다.
- **애플리케이션 독립 프로토콜:** 일반적인 미들웨어를 통해 다양한 원격 애플리케이션에 접근할 수 있도록 하는 범용 솔루션입니다.
### 17. 분포 투명성을 위한 클라이언트 소프트웨어 (26p)
- **클라이언트 소프트웨어의 구성:** UI뿐만 아니라 로컬 처리 및 통신 기능을 포함하며, 임베디드 기기(ATM, 바코드 리더 등)에서는 UI보다 통신 비중이 더 큽니다.
- **분포 투명성 (Distribution Transparency):** 클라이언트는 이상적으로 원격 프로세스와 통신한다는 사실을 인지하지 못해야 합니다.
- **접근 투명성 (Access Transparency):** 서버가 제공하는 인터페이스 정의로부터 **클라이언트 스텁(Client Stub)** 을 생성하여 처리합니다.
    - 스텁은 서버와 동일한 인터페이스를 제공하면서 머신 아키텍처의 차이나 실제 통신 과정을 숨깁니다.
### 18. 위치 및 복제 투명성 구현 (27p)
- **위치, 이주, 재배치 투명성:** 서버 위치가 변경되면 미들웨어가 이를 직접 안내받아 사용자에게는 지리적 위치를 숨깁니다.
- **복제 투명성 (Replication Transparency):** 클라이언트 측 미들웨어가 서버 복제본들에 요청을 보내고 응답들을 수집합니다.
    - **작동 원리:** 클라이언트 앱으로부터 온 요청을 복제하여 여러 서버에 전달하고, 수집된 여러 응답 중 하나만을 앱에 전달하여 복제 사실을 숨깁니다 (그림 3-10).
### 19. 고장, 동시성 및 지속성 투명성 (28p)
- **고장 투명성 (Failure Transparency):** 서버와의 통신 장애를 클라이언트 미들웨어에서 마스킹합니다.
    - **예시:** 연결이 실패할 경우 미들웨어가 자동으로 재시도를 하거나 다른 서버 접속을 시도합니다.
    - **예시:** 웹 브라우저가 서버 연결 실패 시 이전에 캐싱된 데이터를 반환하는 방식입니다.
- **동시성 및 지속성 투명성:** 다른 투명성들에 비해 클라이언트 소프트웨어에서 지원하는 수준이 상대적으로 낮습니다.

### 20. 서버 설계의 주요 이슈: 조직화 (29p)
- **반복 서버 (Iterative Server):** 서버가 요청을 직접 처리하고, 필요 시 요청한 클라이언트에게 응답을 반환합니다.
- **동시 서버 (Concurrent Server):** 서버가 직접 요청을 처리하지 않고 별도의 스레드나 프로세스에 넘긴 뒤, 즉시 다음 요청을 기다립니다.
    - **구현 예시:** 멀티스레드 서버를 사용하거나, UNIX 시스템처럼 새 요청마다 프로세스를 포크(fork)하는 방식이 있습니다.
### 21. 서버 엔드포인트(Port)의 결정 방식 (30-31p)
- **잘 알려진 엔드포인트 (Well-known Endpoints):** IANA에 의해 FTP(21), HTTP(80)처럼 서비스별로 전역 할당된 포트를 사용합니다.
    - 클라이언트는 네임 서비스를 통해 서버의 네트워크 주소만 찾으면 됩니다.
- **동적 엔드포인트 할당 (Dynamic Assignment):** OS에 의해 엔드포인트가 동적으로 할당되는 방식입니다 (예: time-of-day 서버).
    - **데몬(Daemon) 활용:** 서버 머신마다 특별한 데몬을 실행하여 각 서비스의 현재 엔드포인트를 추적합니다.
    - 클라이언트는 먼저 데몬에게 포트 번호를 물어본 뒤 서버에 접속합니다.
### 22. 효율적인 서버 관리: 슈퍼 서버 (32-33p)
- **자원 낭비 문제:** 각 서비스마다 별도의 서버를 상시 가동하는 것은 자원 낭비일 수 있습니다.
- **슈퍼 서버 (Superserver) 솔루션:** 단일 슈퍼 서버가 여러 서비스의 엔드포인트를 동시에 리스닝합니다.
    - **예시:** UNIX의 `inetd` 데몬이 이에 해당합니다.
    - 요청이 들어오면 데몬이 특정 프로세스를 생성(fork)하여 요청을 처리하게 하고, 작업이 끝나면 해당 프로세스는 종료됩니다.
