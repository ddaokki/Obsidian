## 1. 커널 모듈의 배경: 운영체제와 커널 (Slide 3)
임베디드 시스템을 이해하기 위해 가장 먼저 정리해야 할 개념은 **운영체제(OS)와 커널(Kernel)의 관계입니다.
- **Linux Distro (OS):** 우리가 흔히 말하는 '우분투'나 '페도라' 같은 것들입니다. 리눅스 커널을 중심으로 **GNU 도구, 라이브러리, 윈도우 시스템(GUI), 데스크탑 환경** 등이 합쳐진 소프트웨어의 집합체입니다.
- **Linux Kernel:** 운영체제의 가장 핵심적인 '심장' 부위입니다. 하드웨어와 직접 소통하며 자원을 관리하는 역할을 합니다.
> **💡 비유하자면?**
> 
> **운영체제**가 '레스토랑' 전체라면, **커널**은 주방에서 실제로 요리를 하고 재료를 관리하는 '헤드 셰프'와 같습니다. 손님(사용자)은 홀(GUI/라이브러리)에서 주문을 하지만, 실제 일은 주방(커널)에서 일어납니다.

---
## 2. 커널의 두 가지 타입: 모놀리식 vs 마이크로 (Slide 3-6)
커널을 어떻게 설계하느냐에 따라 크게 두 가지로 나뉩니다.
### 2.1 모놀리식 커널 (Monolithic Kernel)
- **구조:** 모든 기능(프로세스 관리, 파일 시스템, 드라이버 등)이 하나의 거대한 프로그램 안에 들어있습니다.
- **장점:** 기능들이 서로 직접 소통하므로 **성능이 매우 높습니다 (High Performance)**.
- **단점:** 덩치가 크다 보니 수정이 어렵고 **유연성이 낮습니다 (Low Flexibility)**.
- 슬라이드 캐릭터: 펭수(거대한 펭귄)
### 2.2 마이크로커널 (Microkernel)
- **구조:** 커널은 최소한의 기능만 담당하고, 나머지는 개별 단위로 쪼개어 엄격한 통신 메커니즘을 통해 동작합니다.
- **장점:** 구조가 독립적이라 **유연하며(Flexibility)** 네트워크를 통해 기능을 분산시킬 수도 있습니다.
- **단점:** 통신 비용이 발생해 **성능이 상대적으로 낮습니다 (Low Performance)**.
- 슬라이드 캐릭터: 뽀로로(작은 펭귄)

## 3. 리눅스 커널의 내부 구조 (Slide 7-8)
리눅스 커널은 **User Space(사용자 영역)**와 **Kernel Space(커널 영역)**로 엄격히 나뉘어 동작합니다.
- **User Space:** 애플리케이션과 라이브러리가 실행되는 곳입니다.
- **Kernel Space:** 리눅스 커널의 핵심 기능들이 위치합니다.
    - **프로세스 및 메모리 관리:** CPU와 RAM을 효율적으로 배분합니다.
    - **가상 파일 시스템(VFS) & 소켓:** 파일 읽기/쓰기와 네트워크 통신을 담당합니다.
    - **디바이스 드라이버:** 하드웨어(CPU, 메모리, 저장장치, 센서 등)를 직접 제어합니다 .
실제로 리눅스 소스 코드의 `/drivers` 디렉토리를 보면 블루투스, USB, 그래픽 등 수많은 장치를 위한 드라이버 코드가 포함되어 있습니다.

## 4. 커널 모듈(LKM)이란 무엇인가? (Slide 9)
드디어 핵심 개념인 **Loadable Kernel Modules (LKM)**입니다.
- **정의:** 실행 중인 커널에 **실시간(Runtime)으로 추가하거나 제거할 수 있는 코드 조각**입니다.
- **커널 모듈이 왜 필요한가요?**
    1. **커널 이미지 최소화:** 모든 드라이버를 커널에 다 집어넣으면 용량이 너무 커집니다. 필요한 것만 그때그때 끼워 쓸 수 있습니다.
    2. **재부팅 불필요:** 모듈 방식이 아니라면, 새로운 기능을 추가할 때마다 **커널을 새로 빌드하고 시스템을 재부팅**해야 합니다.
> **💡 비유하자면?**
> 
> 커널 모듈은 **'레고 블록'**이나 컴퓨터의 **'USB 장치'**와 같습니다. 컴퓨터를 껐다 켤 필요 없이 필요할 때 꽂으면(insmod) 바로 인식되고, 다 쓰면 뽑으면(rmmod) 그만입니다.

## 5. 커널 모듈의 특징 (Slide 11)
커널 모듈은 일반적인 C 언어 프로그램과 환경 자체가 다릅니다. 레고 블록에 비유했던 것처럼, 독립적인 프로그램이 아니라 **이미 돌아가고 있는 커널의 일부**가 되는 것이기 때문이죠.
- **`main()` 함수가 없음:** 일반 프로그램의 시작점인 `main()` 대신, 커널에 들어갈 때와 나갈 때 호출되는 **진입(Entry) 및 종료(Exit) 함수**가 존재합니다.
- **커널 컨텍스트(Kernel Context):** 모듈은 독립적인 프로세스가 아닙니다. 실행되는 순간 **커널 공간(Kernel Space)**의 일부가 되어 동작하므로, 실수하면 시스템 전체가 뻗을 수 있어 매우 주의해야 합니다.
    +1

## 6. 진입(Entry)과 종료(Exit) 함수 (Slide 12-13)
모듈이 커널이라는 거대한 기계에 장착되고 분리될 때의 규칙입니다.
- **`module_init()` & `module_exit()`:** 개발자가 만든 함수를 "이게 시작 함수야!", "이게 끝 함수야!"라고 커널에 알려주는 매크로입니다.
- **함수 정의 규격:**
    - **시작 함수:** `static int __init 함수명(void)` 형태이며, 성공 시 `0`을 반환해야 합니다.
        +1
    - **종료 함수:** `static void __exit 함수명(void)` 형태입니다.
- **`__init`과 `__exit`의 마법:** 이 키워드들은 커널에게 힌트를 줍니다. `__init`은 "이 함수는 로딩할 때만 쓰고 다신 안 쓰니까 메모리에서 지워도 돼!"라고 알려주어 메모리를 절약하게 해줍니다.

## 7. 첫 번째 모듈 코드 예시 (Slide 14)
실제 코드는 대략 이런 모습입니다.
C
```
#include <linux/init.h>
#include <linux/module.h>
MODULE_LICENSE("Dual BSD/GPL"); // 라이선스 명시 (필수는 아니나 권장) [cite: 220]
static int __init hello_init(void) {
    printk(KERN_NOTICE "Hello, World\n"); // 커널 로그에 출력 [cite: 224]
    return 0;
}
static void __exit hello_exit(void) {
    printk(KERN_NOTICE "Goodbye\n"); [cite: 227]
}
module_init(hello_init); [cite: 229]
module_exit(hello_exit); [cite: 230]
```

## 8. 모듈 컴파일하기: Makefile (Slide 15-16)
커널 모듈은 일반 `gcc`로 컴파일하지 않고, **Kbuild**라는 커널 빌드 시스템을 이용해야 합니다.
- **`obj-m := mymod.o`:** 이 한 줄이 핵심입니다. "mymod.o라는 오브젝트 파일을 커널 모듈(`.ko`)로 만들어라"라는 뜻입니다.
    +1
- **여러 파일로 구성된 경우:** `mymod-objs := file1.o file2.o`와 같이 작성하여 합칠 수 있습니다.
- **결과물:** 컴파일이 완료되면 `.c` 파일이 아닌 **`.ko` (Kernel Object)** 파일이 생성됩니다.

## 9. 모듈 관리 명령어 (Slide 17-18)
모듈을 다루는 5가지 필수 명령어를 꼭 기억하세요!

|명령어|역할|특징|
|---|---|---|
|**`insmod`**|모듈을 커널에 **삽입**|파일 경로를 직접 지정해야 함|
|**`modprobe`**|**지능적인** 모듈 삽입/제거 <br><br>+1|**의존성**이 있는 다른 모듈까지 알아서 같이 로드함 <br><br>+1|
|**`lsmod`**|현재 로드된 모듈 **목록 보기**|`/proc/modules`의 내용을 보여줌|
|**`rmmod`**|로드된 모듈 **제거**|사용 중인 모듈은 제거되지 않음|
|**`modinfo`**|모듈의 **상세 정보** 확인|제작자, 설명, 라이선스 등을 표시함|
`insmod`는 단순히 모듈을 꽂는 역할만 하지만, `modprobe`는 "이 장치를 쓰려면 A 모듈 말고 B 모듈도 먼저 필요해!"라는 **의존성(Dependency)**을 파악해서 한 번에 해결해 주는 스마트한 도구랍니다.

## 10. 모듈 라이선스 (Slide 20)
커널 모듈을 작성할 때 `MODULE_LICENSE()` 매크로를 통해 라이선스를 명시해야 합니다. 이는 해당 코드가 어떤 규칙을 따르는지 커널에 알려주는 신분증과 같습니다.
- **GPL:** GNU Public License v2 또는 그 이후 버전을 의미합니다.
- **Dual BSD/GPL:** GPL v2 또는 BSD 라이선스 중 선택 가능함을 의미합니다.
- **Proprietary:** 비공개 소스 제품에 사용됩니다.
- **중요성:** 라이선스를 명시하지 않거나 비자유 라이선스일 경우, 커널은 해당 모듈을 'Tainted(오염됨)' 상태로 간주하며 일부 커널 기능을 사용하지 못할 수도 있습니다.

## 11. 커널 메시지 출력: printk() (Slide 21)
커널 내부에서는 사용자 영역의 `printf()`를 사용할 수 없습니다. 대신 **`printk()`**를 사용합니다.
- **로그 레벨 (Log Levels):** 메시지의 중요도에 따라 0~7까지의 우선순위가 있습니다.
    - **KERN_EMERG (0):** 시스템이 중단되기 직전의 비상 상황.
    - **KERN_ERR (3):** 하드웨어 등의 오류 상태.
    - **KERN_NOTICE (5):** 정상적인 상황이지만 주목할 만한 가치가 있는 경우.
    - **KERN_DEBUG (7):** 디버깅용 메시지.
- **규칙:** 숫자가 작을수록 우선순위가 높습니다.

---
## 12. 콘솔 로그 레벨과 출력 제어 (Slide 22-23)
모든 `printk` 메시지가 화면에 바로 보이는 것은 아닙니다.
- **출력 조건:** 메시지의 로그 레벨이 시스템의 `console_loglevel` 변수보다 작아야(우선순위가 높아야) 현재 콘솔에 즉시 출력됩니다.
- **확인 및 변경:** `/proc/sys/kernel/printk` 파일을 통해 현재 레벨을 확인하거나 변경할 수 있습니다.
- **printk_ratelimit():** 짧은 시간 내에 너무 많은 메시지가 쏟아져 시스템이 마비되는 것을 막기 위해 사용합니다.
    - 정해진 임계치를 넘으면 0을 반환하여 출력을 제한합니다.
    - `/proc/sys/kernel/printk_ratelimit` 파일을 통해 대기 시간을 조절할 수 있습니다.

## 13. 디버깅 메시지 On/Off 기법 (Slide 24)
개발 단계에서는 많은 로그가 필요하지만, 배포 시에는 성능을 위해 이를 꺼야 합니다. 이를 위해 **가변 인자 매크로(Variadic macro)**를 활용합니다.
- **구조:** `MY_DEBUG`라는 기호가 정의되어 있을 때만 `printk`가 동작하도록 매크로를 만듭니다 .
- **컴파일 옵션:** Makefile에서 `ccflags-y=-DMY_DEBUG` 옵션을 주어 소스 코드 수정 없이 디버그 메시지를 켜고 끌 수 있습니다.
> **💡 비유하자면?**
> 
> `printk`의 로그 레벨은 **'스피커 볼륨'**과 같습니다. 중요한 공지(Level 0)는 볼륨이 작아도 들리게 설정되어 있지만, 사소한 수다(Level 7)는 볼륨을 키워놓지(console_loglevel을 높이지) 않으면 들리지 않는 것과 비슷합니다.

## 14. 왜 컴파일 에러가 나지 않을까? (Slide 26)
일반적인 C 프로그램은 `main` 함수에서 정의되지 않은 함수를 호출하면 빌드 시점에 에러가 납니다. 하지만 커널 모듈은 `printk` 같은 함수를 가져다 쓰면서도 컴파일 시점에 에러가 나지 않습니다.
- **해결의 비밀:** 커널 모듈은 **오브젝트 코드** 상태로 존재하며, 실제 함수 주소는 커널에 **적재(insmod)되는 순간**에 결정되기 때문입니다.
- **심볼 테이블(Symbol Table):** 커널은 전역 함수와 변수들의 주소를 담은 '지도'를 가지고 있습니다. 모듈이 로드될 때, 커널은 이 지도를 보고 "아, `printk`는 이 주소에 있구나!" 하고 연결해 줍니다.

## 15. 심볼 공유 (Exporting Symbols) (Slide 27-28)
모듈이 커널의 함수를 쓰는 것처럼, **내가 만든 모듈의 함수를 다른 모듈이 쓰게 할 수도 있습니다.**
- **EXPORT_SYMBOL(함수명):** 내가 만든 함수를 커널 심볼 테이블에 등록하여 누구나 쓸 수 있게 공개합니다.
- **커널 심볼 확인:** 현재 커널에 어떤 심볼들이 있는지 궁금하다면 `/proc/kallsyms` 파일을 확인하면 됩니다.
- **모듈 간 협업:** 한 모듈이 함수를 내놓고(Export), 다른 모듈이 그 함수를 가져다 쓰는 방식입니다.

---
## 16. 심볼이 연결되는 과정: insmod의 내부 (Slide 29)
우리가 `insmod` 명령어를 치면 커널 내부에서는 다음과 같은 일이 벌어집니다.
1. **메모리 할당:** 모듈 코드를 담을 공간을 커널 메모리에 만듭니다.
2. **코드 복사:** 모듈의 내용을 해당 공간으로 옮깁니다.
3. **심볼 해결(Resolve):** 모듈 내에서 외부 함수를 호출하는 부분들을 커널 심볼 테이블의 실제 주소와 연결합니다.
4. **초기화:** 마지막으로 모듈의 시작 함수(`init`)를 실행합니다.

## 17. 실습 예제: Mod1과 Mod2 (Slide 30-33)
이 개념을 이해하기 위해 두 개의 모듈을 만듭니다.
### Mod1: 함수를 제공하는 쪽 (Slide 30)
- `my_func`라는 함수를 만들고 `EXPORT_SYMBOL(my_func)`를 선언합니다.
- 이 모듈이 먼저 로드되어야 `my_func`가 커널 지도에 등록됩니다.
### Mod2: 함수를 사용하는 쪽 (Slide 31)
- `extern void my_func(void)`를 선언하여 외부 어딘가에 이 함수가 있음을 알립니다.
- 코드 내부에서 `my_func()`를 호출합니다.
### 실행 결과 및 주의사항 (Slide 33)
- **Case 1 (실패):** Mod1을 로드하지 않고 Mod2를 로드하면 **'Unknown symbol'** 에러가 발생합니다. 지도가 없으니 길을 잃은 것이죠.
- **Case 2 (성공):** Mod1을 먼저 로드한 후 Mod2를 로드하면 정상 작동합니다.
- **의존성 주의:** Mod2가 Mod1의 함수를 쓰고 있다면, Mod2를 먼저 제거하기 전에는 Mod1을 제거할 수 없습니다.
> **💡 비유하자면?**
> 
> **심볼 공유**는 '라이브러리 도서관'과 같습니다.
> 
> - **EXPORT_SYMBOL**은 도서관에 새 책을 기증하는 것이고,
>
